# 《Lean 4 自动化内幕》作者语言风格档案

状态：中文工作规范。本档案以 Ch02 全文和 Ch03 至 Macro 信息提取 API 表格之前为正面样本；Ch03 从该表格起只作为语言负例，不代表作者文风。

## 1. 真正的分界

子鱼的文字不靠第一人称、笑话、短句或不用表格来辨认。最稳定的特征是：一句话是否参与了读者发现机制的过程。

典型段落通常会完成以下一项或数项工作：

- 从一个具体愿望推出下一个构造；
- 跟着真实输入走过解析、宏展开或证明步骤；
- 找出那个最自然、却会出错的推断；
- 把篇幅花在隐藏边界上，省略读者已经能够推出的部分；
- 回到前面的例子，偿还先前留下的解释债；
- 在读者刚好具备推导能力时，把一步交给他完成。

当文章主要追求覆盖完整时，语言便开始偏离作者：完整分类、平均分配篇幅、换一个标题重复职责图，以及把代码逐项翻译成没有改变读者模型的文字。

## 2. 作者、读者和“我们”

叙述者经常出现，但不是负责暖场的主持人。第一人称通常记录真实的设计选择或接口愿望：

- “假如我不想写列表……”
- “如果我想同时接收这两种写法……”
- “我们能立即想到的一个简单方案……”

第二人称通常交付一个已经足以完成的推断：

- “你可以自己思考一下 `SUBR` 为什么是右结合的。”
- “还记得上一章 `term:max+` 的技巧吗？”

作者很少单纯把读者叫来听预告。除非一句话马上指定将要执行的具体动作，否则不用“我们将探索”“你将学会”“下面让我们看看”。

### 执行规则

- 用“我”说明作者取舍、接口偏好或诚实的能力边界；
- 用“你”交给读者一个明确的推断或实验；
- 用“我们”表示作者和读者正在共同完成同一段推导；
- 中性说明不必为了显得亲切而硬塞人称。

## 3. 词语选择：让普通动词承担技术机制

正面样本偏爱有方向和动作的普通动词。解析器会“读”“继续读”“停下”“吃掉”“失败”“落入”另一个分支；宏会“打包”“匹配”“替换”“抛出异常”“递归调用”；证明术会“拆开”或“关闭”目标。

这不是把机制讲得不准确，而是把状态变化显露出来。与其写：

> `atomic` 提供了解析选择的回滚能力。

不如写：

> 第一个分支已经吃掉左括号才失败，第二个分支就接不到原来的输入了。`atomic` 让解析器失败时退回左括号之前。

先让动作可理解，再给 API 名。

## 4. 句子节奏

正面中文样本的节奏刻意不均匀。一句很短的话可以发起下一轮实验：

> 三次方程仍旧：

后面可以跟一条很长的句子，把完整的因果过程走完。长句成立，是因为每个分句都对应计算中的下一次状态变化。

对正负语料的粗略统计也呈现这种差异：正面样本的平均句长和句长波动都更大；后期 AI 文字更集中在均匀的中等句长。这里不应据此制定字数阈值，真正可复用的是节奏：

1. 短判断或问题；
2. 代码或具体对象；
3. 必要时用长句走完因果链；
4. 用短结果、练习或转场收住。

不要把所有句子修成相近长度，也不要只为了缩短句子而切断一条连续的机制解释。

## 5. 转场来自愿望，不来自文档管理

正面样本常这样推进：

- “有时候我们可能想……”
- “或者我们想……”
- “如果我想同时接收……”
- “或许你会想，能否……”
- “现在重复模式已经出现了……”

当前接口不够方便，或当前例子暴露了缺口，文章才移动到下一步。

较弱的转场只是在管理文档：

- “本节将演示……”
- “下面的表格列出……”
- “这是后文使用的分类地图……”
- “接下来区分四种职责……”

标题已经负责管理文档。标题后的第一段应直接开始智力动作。

## 6. 近指和局部回指

作者常说“这个版本”“那个递归调用”“这一整块”“这两种写法”。这些表达成立，是因为对象就在眼前，作者和读者像是在一起读代码。

不必把每个“这个”都替换成完整技术名。反复写全称会让正文变成生成式文档。但前文若有数个可能对象，就不能使用指向不明的“这”。

## 7. “其实”“实际上”不是自动禁词

正面样本中“其实”“实际上”“也就是说”出现得很多，不能机械删除。它们通常标出三种真实纠正：

1. 再剥掉一层语法糖；
2. 实际解析树与表面外观不同；
3. 句法与语义的边界。

判断标准不是词本身，而是读者能否说出它纠正了哪个模型。如果后一句只是普通事实的换句话说，就应删除。

## 8. 术语在需要时落位

术语往往出现在普通语言动作之后：

- 左边负责匹配，所以叫“匹配模式”；
- 右边给出替换结果，所以叫“展开式”；
- `$roots:term*` 捕获重复子节点，所以这里是“重复反引用”；
- 宏拿不到当前目标，所以必须转入 `TacticM`。

不要用尚未获得用途的正式定义开场。`Syntax` 构造子这样的有限对象已经在前文获得充分动机，可以直接陈列，再用手工构造的具体句法树把它落地。

## 9. 幽默必须咬住技术事实

正面例子包括：

- 由“压缩即智能”推出“宏就是智能！”；
- 去掉语法糖时说“最不甜的版本”；
- 解释封闭定义的维护成本时说“从代码堆翻出来改”；
- 想省掉宏参数时说“因为这明明都可以从题干当中推断出来呀”。

它们分别压缩概念、标出实现层次、指出工程成本或推动接口改进。不要孤立添加“这很简单”“有趣的是”“像魔法一样”。一句玩笑至少要完成以下一件事：压缩概念、暴露痛点、推动下一步。

## 10. 省略本身也是文风

已经能由共同原则恢复的信息，不必逐行解释。示范一两次后，可以留作练习、放入参考表，或直接展示真实源码。

省略判据：

- 读者能从已学材料可靠地组合推出：省略；
- 一个自然但错误的模型会得到错误答案：明确纠正；
- 出现了真正的新原则：即使代码很短也要解释。

因此 Ch02 对 `rewrite` 和 `simp` 的短讲是正面基线，`induction` 中两个缩进基准却值得单独展开。

## 11. 段落内部的运动

典型解释段落常沿以下路径运动：

1. 指定一个输入或想要的接口；
2. 跟着 Lean 实际执行；
3. 在意外分支、失败点或不匹配处停下；
4. 给出解释它的机制；
5. 必要时回头说明这个机制还解释了什么。

每段不必五步俱全，但句子之间应形成一条因果路径。避免把数个同级事实并列成一个段落。

## 12. Ch03 API 表格之后的语言负例

后半章含有新信息，但当前语言只作为负例。

### 12.1 换标题重复解释

宏的能力边界在 API 表前已经由 `poly_roots` 自然撞出，后面又在 API 表说明、“宏能知道什么”和“第一次撞上宏的边界”中反复陈述。多规则顺序和 `trivial` 也重复出现。

新增一节前先问：它是否改变了读者的模型？若只是把旧知识换一种分类重新陈列，应并回首次解释或删除。

### 12.2 在读者产生需要前建立分类图

“tactic 宏主要承担四种工作”形式上完整，却没有从新问题中生长出来。分类图适合放在共同原则已经建立后的参考层，不应反复充当正文骨架。

### 12.3 解释单元过于均匀

后期 AI 文字经常为每项安排一个紧凑段落：源码事实、范围限定、向后预告。每段都很完整，但彼此可以交换。作者正文会把不等难度的问题写成不等篇幅。

### 12.4 把读者已经会读的代码重新翻译一遍

每个句法组件都被转述成文字，却没有指出新的失败路径或设计动机。这样的解释只推迟下一次发现。已经可以组合推出的内容不再逐项翻译。

### 12.5 审计报告腔

后期文字更依赖分号、范围限定、“准确说法是”“通常”“至少”“最好”等表达。区别真正承重时可以使用；连续出现会把教材写成源码审计报告。

### 12.6 后贴的生动感

“一个非常朴素的灾难”“六个互不相干的魔法咒语”“调试会很滑稽”等句子，是在静态说明完成后再补活泼。作者的幽默通常会造成或解释一个转场，不是给既成段落贴表情。

## 13. 先英文、后中文的写作流程

以后先写英文 Markdown 草稿，利用模型在英文中更自然的动作动词和因果组织，把语义动态完整写出来。英文稿只是临时语义脚手架，不是未来英文版的事实源。

### 第一步：先写读者状态 brief

动笔前记录：

- 读者已经能做什么；
- 他现在想做什么；
- 哪些信息可以可靠推出；
- 最可能出现什么误解；
- 本节用什么新能力或奖励收尾。

### 第二步：写英文教学稿

英文使用明确主语和直接动词。优先用可运行例子，不先搭分类图。让改进接口的欲望逼出抽象和边界。参考材料与叙事正文分开。

### 第三步：生成完整中文初稿

中文版保留每段的教学功能和事实，但不必保留英文的从句顺序、代词、冠词、被动式或连接词。

常见修正：

- 英文被动句改成明确动作主体或事件顺序；
- 抽象名词改成具体动词；
- `This means that...` 直接写结论；
- 过长前置定语拆成先行条件；
- `however/therefore/additionally` 只保留中文真正需要的逻辑关系；
- 解释机制时，把英文系词定义改成动作过程。

中文必须已经是完整正文，不能只是把提纲扩成几组要点。中文初稿完成后即成为当前工作文本；临时英文稿可以归档，但不再约束中文后续修改。

### 第四步：从初稿恢复真实语义动态

暂时放下提纲，只读中文初稿，重新记录这一节实际发生了什么：读者的愿望在哪里变化，能力在哪里复利，哪个例子留下残差，参考层何时变得正当，哪道边界逼出了下一层抽象。若初稿出现了比提纲更好的运动，应修改提纲描述现实，而不是把正文压回旧计划。

### 第五步：逐句执行行动审计

给每句话标出行动：激发动机、指定操作、跟踪执行、制造意外、诊断、纠错、命名、限定、回扣、交付练习或转入下一层。没有独特行动的句子删除或重写。随后反复做必要性、精确性、节奏和作者关系四轮推敲。

### 第六步：运行费曼学习者 pipeline

逐句精修形成完整稿后，才交给隔离的零先验学习者复述和操作。每次修复最早误解原因，禁止追加百科补丁。句子审计和学习者复测反复执行，直到连续两轮敌意检查没有新的实质问题。

## 14. 草稿生命周期、解释预算和未来英文出版

工作链是：

```text
每节设计卡 → 提纲 → 临时英文语义稿
→ 完整中文初稿 → 逐句行动精修
→ 费曼学习者循环 → 子鱼修改后的最终中文
```

最终中文可以与临时英文完全不同，不维护段落映射，也不要求双语同构。

### 解释预算

- **B0，不解释**：前文原则已经完全决定结果，只保留代码或引用。
- **B1，一句截断误解**：读者大体能推出，但可能沿一个具体的错误模型继续。
- **B2，局部解释**：当前例子引入新机制，但不需要展开完整实现。
- **B3，执行轨迹或反例**：用于结合性、回退顺序、阶段边界、失败后状态、卫生性等会污染后续理解的节点。

分配预算时只问三件事：读者能否可靠推出；推错后是否会形成持续错误；后续例子是否马上复用这项解释。不能因为同一声明里出现了数个 API，就给它们分配相同篇幅。

以后正式发布英文版时，以子鱼最终修改的中文为唯一内容基线，重新翻译成自然英文，再单独制作 English Verso。早期英文稿不是 canonical source，不能用来覆盖中文定稿中的后续决定。

## 15. 小型双语基线

### English draft

The repeated pattern has now appeared. The quadratic and cubic proofs perform the same two steps; only the polynomial, the roots, and the variable change. A fixed macro template still cannot handle both examples because the number of factors changes. The simplest repair is to pass the roots as a list and build

\[
\prod_i (x-r_i).
\]

Before writing the macro, let us rewrite the cubic proof in that form. This checks that the representation really removes the difference we intend to abstract away.

### 中文定稿

现在重复模式已经出现了。二次和三次证明都只做两步，变化的只有多项式、根和变量；但因式数量不同，还不能直接塞进同一个固定模板。最简单的办法是让调用者传入根列表，再统一构造

\[
\prod_i(x-r_i).
\]

先别急着写宏。我们先把三次证明改成这个形式，确认根列表确实消掉了我们想抽象的差异。

中文版没有机械复制英文从句，而是恢复作者节奏：短观察、压缩对照、数学对象、下一步具体动作。
