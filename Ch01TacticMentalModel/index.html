2. tactic 心智模型🔗

本章目标：暂不依赖 Lean 的真实实现，从命题、假设、目标和证明出发设计一个 tactic 系统。每个例子都会暴露当前设计无法满足的约束，并给出最小扩展。最后，我们从顺序组合的需求中导出 monad，同时说明选择与回滚为什么需要额外接口。

本章不写 Lean：这一章正文里不会出现任何真实的 Lean 定义、import、或库里的 API 名字。全部用伪代码。下一章再把这里发明的每个零件对到 Lean 的现实实现上。

本章不从四层 monad 的定义开始，而是问：如果 tactic 系统尚不存在，只凭命题与证明，需要哪些数据和操作才能把它造出来？

推导按同一原则推进：先给出最小设计，再用具体例子检验；当前表示无法满足新约束时，只增加解决该问题所需的机制。这样得到的抽象都有明确来源，也能看出它与 Lean 实际实现之间的差距。

先说清楚一件事：本章所有代码块都标着 \[伪代码\]。它们不是 Lean，不能编译，也别去 Lean 里搜这些名字。它们只是一种够精确、让你能在任何普通语言里照着实现出来的记法。

2.1. 先划一块地：我手里有什么🔗

先列出系统处理的基本对象。

命题：一个可以为真或为假的数学陈述。P ∧ Q、P → Q、n + 0 = n 都是命题。我暂时不关心命题内部长什么样，只把它当成一个能比较、能拆开的对象。

证明：一个命题为真的凭据。在本章设计的系统中，证明是能够独立检查的对象，不是“已经证完”的声明。给定命题 P 和候选证明，系统必须能检查该对象是否确实证明 P。因此，关闭目标不能只从待办列表中删除一项；它必须产生能够通过检查的证明对象。

目标：一个“待证任务”。它至少包含一个我要证的命题，还包含我在证它时手头能用的局部假设。写下来大概是这个形状：

[伪代码]

Goal = {
  hypotheses : 一列 (名字, 命题)   -- 局部上下文：我现在能用的假设
  target     : 命题                -- 我要证的命题
}

举个具体的。要证 P → (Q → P)，我通常不会一口气证它，而是先把两个前提搬进假设，把问题变成“在 h1 : P、h2 : Q 之下证 P”。这时的目标是：

[伪代码]

Goal = {
  hypotheses = [ (h1, P), (h2, Q) ]
  target     = P
}

注意 hypotheses 是给证明用的原料库，target 是当前要交付的东西。这两样必须分开记：它们的角色不同，一个是我能反复取用、引用的，一个是我要生产的。

成功与失败：tactic 必须表达两种结局。“目标形状不符”“局部假设中没有匹配项”都应成为明确的失败结果，而不是程序崩溃或伪造成功。

基本对象共有四类：命题、可检查的证明、由假设与待证命题组成的目标，以及成功或失败的执行结果。后文的状态、环境、失败通道和组合器都从这些对象及其操作需求中导出。

2.1.1. 三样东西别搅在一起🔗

动手前先把三个层次分清楚，否则后面必乱。

  1. 被证的数学对象：命题和它的证明。这是静态的、数学的东西。P → (Q → P) 为真这件事，跟我用什么顺序去证它没关系。

  2. 会变的搜索状态：我证明过程中那份不断变化的“待办”。一开始只有一个目标；intro 之后目标的假设变多了、待证命题变小了；constructor 之后目标从一个变成两个。这份状态是可变的、会转移的。

  3. tactic 程序本身：一段读当前状态、改状态、同时往外攒证明的程序。intro、exact、constructor 都是这种程序。

容易混淆的是前两层：目标列表属于搜索状态，不是证明本身。列表可以增减或重排；只有构造出通过检查的证明对象，证明才算完成。后文每个 tactic 都必须保持这一区分。

2.2. 造一个搜索状态：先从一个目标试起🔗

先采用最小假设：搜索状态中只有一个目标。后文在该表示无法容纳必要结果时再扩展它。

[伪代码]

State = {
  goal  : Goal 或 “无”      -- “无” 表示：没有待办目标了
  proof : 一个“带洞的证明”
}

状态必须携带 proof。如果 tactic 只修改目标，那么目标列表清空后仍没有可供检查的证明对象。proof 因而保存一份逐步补全的证明骨架。

这份骨架可以含有尚未构造的洞。tactic 选择一个洞并填入证明结构；新结构可能产生更多洞，也可能直接完成该处证明。所有洞都被合法填入后，骨架才成为完整证明。

给每个洞一个名字。方框不能是匿名的，否则一旦出现两个长得一样的方框，我就说不清“我到底在填哪一个”。所以每个洞都带一个稳定的身份标签，记作 HoleId，写成 ?h0、?h1 这样。证明骨架里的洞用它的 HoleId 标记；而每个目标都要记住自己负责填哪个洞，于是 Goal 多一格：

[伪代码]

Goal = {
  id         : HoleId              -- 我负责填证明骨架里的哪个洞
  hypotheses : 一列 (名字, 命题)   -- 局部上下文：我现在能用的假设
  target     : 命题                -- 我要证的命题
}

由此得到贯穿全章的不变量：证明骨架中的未填洞与搜索状态中的未解决目标一一对应。每个洞 ?h 恰好对应一个 id = ?h 的目标，反之亦然。关闭目标就是合法填入其对应的洞。

起始状态的证明骨架只有洞 ?h0，目标则是 id = ?h0 的 Goal。目标记录待填洞及其局部假设和待证命题；证明骨架记录已经构造的部分。tactic 成功表示其执行结果符合语义，不保证状态改变，更不保证目标数减少。

2.3. 发明第一批 tactic🔗

下面按约束逐步增强的顺序设计 tactic。每节给出当前状态、朴素实现、执行轨迹，以及该实现尚未满足的条件。

眼下状态里只有一个目标 state.goal，tactic 就作用在它身上。等某个 tactic 无法由单目标状态表示时，再扩展状态。

2.3.1. exact：直接交一个证明🔗

最简单的 tactic：我手上已经有一个证明对象 p，我想用它关掉当前目标。数学上就是“这个目标我会证，证明就是 p”。

当前状态：主目标 g，它的待证命题是 g.target。我带着一个证明对象 p 来。

朴素实现：

[伪代码]

exact(p) = fun state =>
  let g = state.goal
  if 检查(p 是 g.target 的合法证明) then
    -- 把带洞证明里、id 为 g.id 的那个洞，用 p 补死
    let newProof = 在 state.proof 中把洞 g.id 替换成 p
    成功， newState = { goal = 无, proof = newProof }   -- 洞填完了，没有待办了
  else
    失败("给的证明和目标对不上")

执行轨迹：证 P，手里有假设 h1 : P。起始状态为 goal = (id=?h0, target=P, hyps=[h1:P])，证明骨架为 ?h0。调用 exact(h1) 后，检查确认 h1 是 P 的证明。洞 ?h0 被填为 h1，证明骨架完整，目标变为“无”。

必须保持的健全性条件：检查(p 是 g.target 的合法证明) 不能省略。若 exact 不检查 p 就把目标设为“无”，目标列表虽然清空，却没有得到合法证明。任何关闭目标的 tactic 都必须先检查候选证明，再填入对应的洞；检查失败则走失败通道。

2.3.2. assumption：在假设里翻找🔗

exact 要我手动报出证明。更聪明一点：让 tactic 自己去局部假设里翻，看有没有哪个假设正好就是目标。

当前状态：主目标 g，它带着一列假设 g.hypotheses。

朴素实现：

[伪代码]

assumption = fun state =>
  let g = state.goal
  for (name, prop) in g.hypotheses do
    if prop 与 g.target 相同 then
      -- 找到了：这个假设本身就是目标的证明
      return exact(名为 name 的那个假设)  应用到 state
  失败("没有假设能匹配目标")

执行轨迹：目标 target = Q，假设 [ (h1, P), (h2, Q) ]。循环：h1 : P，P 不是 Q，跳过；h2 : Q，命中，用 h2 走一遍 exact，关掉目标。成功。若假设里根本没有 Q，循环走完，落到最后一行，失败。

当前模型尚未定义的判定：prop 与 g.target 相同 不能简单理解为字符相等。Nat 与 ℕ，以及可通过规约化成同一表达式的两项，都可能应被视为相同。真实系统使用定义等价判定；该判定还可能修改求解状态。本章暂将其视作朴素相等，下一章再给出 Lean 的实现。

重复的失败分支：exact 和 assumption 都要构造失败结果。随着 tactic 增多，调用方还会重复处理“成功则继续、失败则短路”的分支。组合器一节会统一这部分结构。

2.3.3. intro：把前提搬进上下文🔗

证 A → B 的标准动作是先假设 A，再证明 B。目标数仍为一，但目标内容已经改变，证明骨架也需要相应扩展。

当前状态：主目标 g，g.target 形如 A → B。

朴素实现：

[伪代码]

intro(name) = fun state =>
  let g = state.goal
  match g.target with
  | (A → B) =>
      let h' = 新建一个 HoleId                          -- 给新洞起个名，比如 ?h1
      let g' = {
        id         = h'                                 -- 新目标负责填新洞
        hypotheses = g.hypotheses ++ [ (name, A) ]      -- 多了一条假设
        target     = B                                  -- 待证命题变小
      }
      -- 关键：把 id 为 g.id 的洞，替换成一个 lambda，
      -- 它接收一个 A 的证明（叫 name），函数体是新洞 ?h'。
      let newProof = 在 state.proof 中把洞 g.id 替换成
                     (fun name : A => ?h')
      成功， newState = { goal = g', proof = newProof }
  | _ => 失败("目标不是箭头类型，intro 无从下手")

执行轨迹：证 P → (Q → P)。起始目标 id=?h0, target = P → (Q → P)，假设 []，证明骨架 ?h0。

  • 调 intro(h1)：目标匹配 A=P、B=(Q → P)。新洞 ?h1，新目标 id=?h1, target = Q → P，假设 [(h1,P)]。证明骨架：fun h1 : P => ?h1。目标数：1 → 1。

  • 再调 intro(h2)：目标匹配 A=Q、B=P。新洞 ?h2，新目标 id=?h2, target = P，假设 [(h1,P),(h2,Q)]。证明骨架：fun h1 : P => fun h2 : Q => ?h2。目标数：1 → 1。

  • 现在目标是“在 h1:P, h2:Q 下证 P”。调 assumption，命中 h1，洞 ?h2 被补成 h1。目标数：1 → 0。

最终证明骨架：fun h1 : P => fun h2 : Q => h1。这是一个完整、可检查的证明对象。

intro 用 lambda 替换旧洞，并创建一个对应函数体的新洞。目标数保持为一，但证明骨架已经推进；洞与目标的一一对应仍然成立。这说明 tactic 的语义是合法更新证明状态，而不是单纯减少目标。

这三步还显示了状态接力的必要性。intro 更新 state.proof 与主目标，assumption 再读取前一步留下的同一份状态并填入叶子。朴素实现必须显式把每一步的 newState 交给下一步。单个 tactic 尚可容忍，组合多步时就会重复出现这条状态链；then 一节将把问题完整展开。

2.3.4. constructor：一个目标裂成两个🔗

现在轮到那个真正撞破“只有一个目标”的 tactic。证 P ∧ Q，要分别证 P 和 Q，再把两个证明合成一个 P ∧ Q 的证明。

主目标 g 满足 g.target = A ∧ B，并对应证明骨架中的洞 g.id。合取证明形如 合取证明 <A的证明> <B的证明>，因此洞 g.id 应替换为 合取证明 ?hL ?hR，产生两个新洞。根据不变量，还需要两个目标：id=?hL, target=A 与 id=?hR, target=B。

当前 State 只有一格 goal，无法同时容纳两个目标。exact 与 intro 都能由单目标状态表示，constructor 则要求把它扩展为目标列表。

现在才扩状态，把 goal 从“一个或无”升级成“一列”：

[伪代码]

State = {
  goals : 一列 Goal      -- 待处理目标列表，空列表 = 没有待办
  proof : 带洞证明
}

补充两个记法：focus(state) 取得列表首个目标，约定为 tactic 默认作用的主目标；rest(state) 表示其余目标。此前的 exact、assumption、intro 只需将 state.goal 换成 focus(state)，再把结果放回列表。exact 关闭主目标后返回 { goals = rest(state), ... }；intro 返回 { goals = [g'] ++ rest(state), ... }。空列表表示没有待办目标。

朴素实现：

[伪代码]

constructor = fun state =>
  let g = focus(state)
  match g.target with
  | (A ∧ B) =>
      let hL = 新建一个 HoleId
      let hR = 新建一个 HoleId
      let gLeft  = { id = hL, hypotheses = g.hypotheses, target = A }
      let gRight = { id = hR, hypotheses = g.hypotheses, target = B }
      -- 关键：把洞 g.id 替换成 合取证明，它的两个参数就是两个新洞
      let newProof = 在 state.proof 中把洞 g.id 替换成
                     (合取证明 ?hL ?hR)
      成功， newState = { goals = [gLeft, gRight] ++ rest(state), proof = newProof }
  | _ => 失败("目标不是合取，constructor 用不上")

执行轨迹：证 P ∧ P，手里有 h : P。起始 goals = [ (id=?h0, target=P∧P, hyps=[h:P]) ]，证明骨架 ?h0。

  • 调 constructor：洞 ?h0 填成 合取证明 ?hL ?hR，目标变为 [ (id=?hL, target=P), (id=?hR, target=P) ]，数量从 1 增至 2。两个目标的待证命题都是 P，但 id 分别为 ?hL 与 ?hR，因此仍可区分。

  • 主目标是 id=?hL 的 P。调 assumption，命中 h，洞 ?hL 补成 h。目标数：2 → 1。剩下 id=?hR 的 P。

  • 调 assumption，命中 h，洞 ?hR 补成 h。目标数：1 → 0。

最终证明骨架：合取证明 h h。完整、可检查。

assumption 减少目标，intro 保持目标数，constructor 增加目标。目标数量不是衡量 tactic 是否推进证明的通用标准。

constructor 创建的两个洞各有稳定身份，并同属一个合取证明。本章模型没有表达更强的跨洞依赖：填入 ?hL 不会限制 ?hR 可以填什么。Lean 的元变量系统会补上这种共享约束。

2.3.5. skip 与 swap：证明不动，只动脚手架🔗

再看两个只改变部分状态的 tactic。

skip 什么都不做，直接成功：

[伪代码]

skip = fun state => 成功， newState = state

它成功了，但目标和证明骨架都不变。因此，“成功”只表示这一步没有失败，不表示取得进展。

swap 把前两个目标调换顺序：

[伪代码]

swap = fun state =>
  match state.goals with
  | [g1, g2, ...rest] =>
      成功， newState = { goals = [g2, g1, ...rest], proof = state.proof }
  | _ => 失败("目标不足两个，没法交换")

swap 不改变目标数或证明骨架，只重排处理顺序。顺序本身是搜索策略的一部分；在真实元变量系统中，先处理一个目标还可能通过共享约束确定其他目标中的元变量，本章模型暂不表达这种联动。

不同 tactic 改变状态的不同部分：exact 改变目标列表和证明，intro 改变主目标内容和证明，constructor 增加目标并扩展证明，swap 只改变列表顺序，skip 保持状态不变。因此，tactic 应建模为具有多种合法转移的状态变换。

2.4. 让 tactic 组合起来🔗

单个 tactic 有了，但真实证明是把它们串起来用的：先 intro，再 constructor，然后每个分支各自 assumption。我需要组合器。造组合器的过程，会把前面攒下的所有痛点集中引爆。

2.4.1. then：先做这个，再做那个🔗

最基本的组合：t1 then t2，先跑 t1，成功后在它产出的状态上接着跑 t2。

朴素实现：

[伪代码]

(t1 then t2) = fun state =>
  match t1(state) with
  | 失败(e)      => 失败(e)              -- t1 没成，整体没成
  | 成功(state1) => t2(state1)          -- 把 t1 的新状态交给 t2

执行轨迹：证 P → (P ∧ P)。用 intro(h) then constructor then assumption（先不管 assumption 只作用主目标的问题，下一节修）。

  • intro(h)：目标 P ∧ P，假设 [h:P]；证明骨架 fun h:P => ?h1。

  • constructor：目标裂成 [P@?hL, P@?hR]；证明骨架 fun h:P => 合取证明 ?hL ?hR。

  • assumption：只关掉主目标那个 P@?hL……第二个 P@?hR 还开着。

顺序组合出现的公共样板：then 先拆开 t1 的结果。失败时原样短路；成功时把新状态传给 t2。每个顺序组合点都会重复这段分支，并显式维护 state → state1 → state2 的接力。后文的 bind 将抽出这一结构。

2.4.2. orElse：不行就换一招🔗

第二个组合：t1 orElse t2，先试 t1，如果它失败，就退回原状态、改试 t2。这是搜索和回溯的雏形。

朴素实现：

[伪代码]

(t1 orElse t2) = fun state =>
  match t1(state) with
  | 成功(state1) => 成功(state1)
  | 失败(_)      => t2(state)      -- 注意：交给 t2 的是原始 state，不是 t1 弄脏的

执行轨迹：目标 Q，假设 [h1:P, h2:Q]。跑 exact(h1) orElse assumption。

  • exact(h1)：h1:P，P 不是 Q，失败。

  • 回退，用原始 state 跑 assumption：命中 h2，成功。

选择组合额外要求事务语义：交给 t2 的必须是原始 state。t1 可能在失败前已经创建目标、扩展证明骨架或填入部分洞；这些修改不能泄漏到备用分支。

因此，orElse 要么提交 t1 的完整成功结果，要么丢弃该分支的全部状态修改。在当前值语义模型中，调用方仍保留原始状态，恢复只需舍弃失败结果。若状态改为原地更新的可变引用，orElse 就必须在运行 t1 前存档，并在失败后恢复。回滚是额外的实现策略，不由 monad 或状态接口自动提供。

2.4.3. first、repeat、以及作用到哪些目标🔗

有了 orElse，多路选择 first 就是把它串起来：

[伪代码]

first([t1, t2, ..., tn]) = t1 orElse t2 orElse ... orElse tn

“重复直到不能再做”是 repeat：

[伪代码]

repeat(t) = fun state =>
  match t(state) with
  | 失败(_)      => 成功(state)        -- 做不动了，就停在当前状态（注意：整体算成功）
  | 成功(state1) =>
      if state1 与 state 在可回溯证明状态上相同 then
        成功(state)                    -- 成功但没进展：也必须停，否则 repeat(skip) 永不结束
      else
        repeat(t)(state1)              -- 做成且有进展，在新状态上接着重复

repeat 也需要回滚：最后一次 t 失败时，应返回该次调用前的状态，并丢弃失败分支的修改。它还必须检查进展；skip 会成功却不修改状态，若仅以成功作为继续条件，repeat(skip) 将永不终止。

assumption、exact 默认只作用于主目标，但 constructor 会产生多个目标，因此还需要“作用于所有目标”的组合器。实现时不能把单个目标从完整状态中剥离，否则会违反洞与目标一一对应的不变量。组合器必须始终持有完整状态，只移动焦点，并按目标的稳定 id 遍历：

[伪代码]

allGoals(t) = fun state =>
  -- 先给此刻要处理的每个目标记下稳定 id（快照：处理过程中 goals 会变）
  let todo = [ g.id for g in state.goals ]
  let mutable cur = state              -- 始终持有完整状态：所有目标 + 整份证明骨架
  for hid in todo do
    if cur.goals 中已经没有 id = hid 的目标 then
      continue                         -- 前一次 t 可能顺手关掉了它；稳定身份不等于目标永远存活
    -- 把焦点移到 id 为 hid 的目标上：只是把它重排到列表最前，
    -- 其余目标、整份 proof 一格都不丢，原样留在 cur 里
    cur = 把 cur 的 goals 重排成“id 为 hid 的目标排在最前”
    match t(cur) with                  -- t 作用在主目标 hid 上，但它看得见完整状态
    | 失败(e)    => return 失败(e)      -- 有一个目标搞不定，整体失败
    | 成功(cur') => cur = cur'          -- t 可能关掉 hid、也可能把它换成若干新目标；完整状态整体接力
  成功， newState = cur

注意它和早先那种“把 [g] 拼到完整证明骨架上”的错误写法的区别：这里从没有把目标从它所属的状态里剥离出来，t 每次拿到的都是一份合法的完整状态，只是主目标换了人。遍历靠的是快照下来的稳定 id，而不是列表位置。稳定身份保证“目标还活着时能准确找到它”，却不保证它永远活着：前一次 t 可能顺手关掉后面的目标，所以每轮先查它是否仍在队列中；已经解决的就跳过。至于 t 新产生的目标，不在最初快照里，本次 allGoals 不额外处理。

执行轨迹：接上一节 P → (P ∧ P) 的现场，constructor 之后目标是 [P@?hL, P@?hR]，todo = [?hL, ?hR]。跑 allGoals(assumption)：先把焦点移到 ?hL，assumption 命中 h、补死洞 ?hL；再把焦点移到 ?hR（靠 id 找到它，哪怕它俩待证命题都是 P 也分得清是哪个），assumption 命中 h、补死洞 ?hR。最终 fun h:P => 合取证明 h h。完整。

于是整条证明可以写成：intro(h) then constructor then allGoals(assumption)。

allGoals 再次出现“成功时接续完整状态，失败时短路”的顺序样板。orElse 的分支则不同：它在失败时捕获错误、恢复状态并改走另一条路径。两种组合不能混为一谈。

这个实现还同时暴露三类贯穿子调用的数据：每次调用都要读取的共享背景，必须一路保留并更新的完整证明状态，以及任一步都可能触发的失败通道。顺序组合负责传递状态并短路失败；只读背景尚未进入当前 Machine 的类型，后文会用化简规则表说明它为什么需要独立通道。

2.4.4. 一个会返回值的 tactic：先查询，再依据结果行动🔗

此前的 tactic 只通过状态变化产生信息，普通返回值都是 Unit。实际证明还需要查询型 tactic 先返回一个值，再由该值决定下一步。固定的 then 会丢弃返回值，无法表达这种依赖。

举个具体的、我们材料库里就能造的例子。造一个查询型 tactic findHyp(prop)：它在主目标的假设里找一条类型为 prop 的假设，找到就把那条假设的名字当返回值交出去，一个证明都不关、状态一格不动：

[伪代码]

findHyp(prop) = fun state =>
  let g = focus(state)
  for (name, p) in g.hypotheses do
    if p 与 prop 相同 then
      return 成功(返回值 = name, newState = state)   -- 状态不动，只把找到的名字交出去
  失败("没有类型为该命题的假设")

它返回的 name 是普通值，不是状态变化。若目标为 A ∧ B，可以分别查找 A 与 B 的假设，再将返回的名字用于构造合取证明。后续的 exact 依赖前两次查询结果：

[伪代码]

证明 A ∧ B 的程序 = fun state0 =>
  match findHyp(A)(state0) with
  | 失败(e) => 失败(e)
  | 成功(nameA, state1) =>                 -- 拿到第一个返回值 nameA
      match findHyp(B)(state1) with
      | 失败(e) => 失败(e)
      | 成功(nameB, state2) =>             -- 第二个返回值 nameB
          exact(合取证明 nameA nameB)(state2)   -- 关键：这一步真的用到了 nameA、nameB

执行轨迹：目标 A ∧ B，假设 [ (ha, A), (hb, B) ]。findHyp(A) 返回 nameA = ha；findHyp(B) 返回 nameB = hb；exact(合取证明 ha hb) 把洞补死。证完。

返回值依赖要求更一般的组合：这里既要接续 state0 → state1 → state2，又要把 nameA、nameB 交给后续步骤。固定的 then 会丢弃前一步结果，无法表达这种依赖。因此，tactic 的结果必须同时包含普通返回值 A 和新状态，组合器再用 A 构造下一步计算。

2.5. 受够了重复：把共同的形状抽出来🔗

现在抽取这些实现反复出现的共同结构。先把 tactic 的类型摊平。

一个 tactic，本质上是这个形状的函数：

[伪代码]

Tactic = State → 结果

而“结果”不是单纯的新状态，它是“失败信息 或 （某个返回值 × 新状态）”。前面几个 tactic 返回值都是“没什么可返回的”（记作 Unit），但刚才 findHyp 已经把话挑明了：一个查询型 tactic 要返回它查到的东西（那条假设的名字），而且下一步真的会用到这个返回值。所以更诚实的形状是：

[伪代码]

Tactic 产出 A  =  State → ( 失败(Error)  或  成功(A, State) )

读作：一台机器，喂给它一个 State，它要么失败给你一个 Error，要么成功给你一个普通返回值 A 和 一个新 State。把它记成一个类型：

[伪代码]

Machine A  =  State → Result A
Result  A  =  失败(Error)  |  成功(A, State)

当前 Machine A 显式表达两种能力：可读写的 State，以及 Error 失败通道。真实 tactic 还需要共享的只读环境和选项，但它们尚未出现在这个类型中；后文会将只读背景作为独立输入加入。

2.5.1. 把普通值塞进机器：pure🔗

skip 需要“成功而不修改状态”。更一般地，给定普通值 a，我们需要一台不修改状态、不会失败、直接返回 a 的机器。

按 Machine A 的定义把它写出来，只有一种写法：

[伪代码]

把值塞进机器(a) = fun state => 成功(a, state)     -- 状态原样穿过，直接成功返回 a

这就是 skip 在任意返回类型上的推广，记作 pure。对已经确定的 Machine A = State → Result A，若要求“不改状态、不失败、返回 a”，实现便只能把原状态与 a 一同放进成功结果。pure(a) 由此将普通值 a 放入计算，同时保持状态不变。

2.5.2. 把两台机器接起来：bind🔗

then、allGoals 和 findHyp 的组合都需要同一操作：先运行机器 m；若成功得到返回值 a 和新状态，就由 a 决定下一台机器 k(a)，并在新状态上继续；若失败，则直接短路。把这一操作抽出：

[伪代码]

接起来(m, k) = fun state =>
  match m(state) with
  | 失败(e)          => 失败(e)             -- m 失败：短路，k 根本不跑
  | 成功(a, state1)  => k(a)(state1)        -- m 成功：把返回值 a 喂给 k，把新状态 state1 传下去

这一定义完成三项工作：

  • 传递状态：m 产出的 state1 交给 k(a)，无需显式维护中间状态链。

  • 短路失败：m 失败时不运行 k，错误原样返回。

  • 传递返回值：a 进入 k，后续计算可以依赖前一步结果。

给它起名：bind，记作 m >>= k。

先看它怎么把丢弃返回值的 then 一句话重写：

[伪代码]

(t1 then t2)  =  t1 >>= (fun _ => t2)      -- t1 的返回值用不上，丢掉，接着跑 t2

findHyp 的组合需要使用前一步返回值，因此必须使用 bind：

[伪代码]

证明 A ∧ B 的程序  =
  findHyp(A)  >>= fun nameA =>       -- 拿到返回值 nameA，绑给下一步
  findHyp(B)  >>= fun nameB =>       -- 再拿 nameB
  exact(合取证明 nameA nameB)       -- 用上前两步的返回值

与手写的嵌套 match 相比，这段代码省去了显式状态接力和失败分支，同时保留 nameA、nameB 到最后一步的数据依赖。值依赖组合因此可以写成平铺的 >>= 链。

一串纯顺序的 tactic 也从此能顺畅写下去：

[伪代码]

证明 P → (P ∧ P) 的程序  =
  intro(h)          >>= fun _ =>
  constructor       >>= fun _ =>
  allGoals(assumption)

每个 >>= 都按定义传递状态与证明骨架，并在失败时短路。

bind 传递状态并短路失败，但不提供回滚或失败后的分支选择。orElse 的选择与恢复语义需要单独接口。

2.5.3. 第二种接口：选择与回滚（pure/bind 造不出它）🔗

pure 和 bind 处理顺序及值依赖组合。orElse、first、repeat 还需要失败捕获与状态恢复，必须另设接口。

bind 只在 m 成功时运行后续计算；失败时直接返回错误。orElse 则要捕获失败、恢复运行 m 之前的状态，并尝试另一分支。这要求两项额外能力：

  • 捕获失败：能拦住本来要冒泡出去的错误，把控制权夺回来（而 bind 遇失败只会放行冒泡）；

  • 回退状态：把 m 弄脏的状态丢弃、复原到它跑之前（前面 orElse 那节反复强调过，这份回滚不是白来的，取决于状态怎么实现）。

因此另设 orElse（也可称 catch/choice）接口：

[伪代码]

(t1 orElse t2) = fun state =>
  存档 state                          -- 回滚要用（值实现里就是攥着原始 state）
  match t1(state) with
  | 成功(a, state1) => 成功(a, state1)
  | 失败(_)         => t2(存档的 state)   -- 捕获失败、回退、改走 t2

orElse 与 bind 可以配合使用，但不能由 pure 和 bind 单独组合出来，因为 bind 不提供失败捕获。first 是一串 orElse；repeat 也依赖捕获失败并恢复到失败前状态。

把两条线钉清楚，这是本章最容易被含糊过去、也最要命的一处分工：

  • 顺序 / 值依赖组合 → pure + bind。这是 monad 的核心两件套。

  • 回退 / 选择 / 搜索 → 一个额外的 orElse/catch 接口 + 一份明确的回滚策略。repeat、first 依赖它。

monad 的 pure 和 bind 只规定顺序组合。回溯搜索需要额外的选择接口和正确的状态恢复策略。

2.5.4. 只读背景：它凭什么不一样🔗

下面加入只读背景。假设一组化简 tactic 都要读取同一张化简规则表。这张表在整段证明中保持不变，却要供 simp、其子调用以及 allGoals 产生的各个调用反复读取。

这份规则表该放哪？

  • 放进每个 Goal 会造成重复。规则表与具体目标无关，而局部假设才是每个目标各自携带、会随 intro 扩展的数据。

  • 放进可写的 State 虽然可行，却允许任意 tactic 修改规则表。原本可由类型保证的只读性质，便只能依靠人工检查。

所以正确的做法是给它单独一格，一个只进不出的只读通道。把机器的形状扩一格：

[伪代码]

Machine A  =  Env → State → ( 失败(Error) | 成功(A, State) )
                ^^^ 只读背景（如那张化简规则表）：每一步都能拿到，但没有“写回新 Env”的出口

Env 只出现在输入侧，输出只有 (A, State)，没有新 Env。这个类型形状保证计算不能通过该通道修改背景。若子计算需要临时使用另一份背景，应提供带作用域的局部替换操作；子计算结束后恢复原背景。

别让 pure/bind 在扩格后掉队：形状多了 Env 这一格，前面定义的 pure、bind 得跟着抬一层，把 Env 原样透传下去。改动很小：

[伪代码]

pure(a)   = fun env => fun state => 成功(a, state)          -- env 读得到，但原样不改
m >>= k   = fun env => fun state =>
  match m(env)(state) with                                  -- 把同一个 env 交给 m
  | 失败(e)         => 失败(e)
  | 成功(a, state1) => k(a)(env)(state1)                    -- 再把同一个 env 交给 k

例如 readRules >>= fun rules => simpWith(rules)：readRules 从 env 取得规则表，不修改 env 或 state；bind 将同一个 env 与前一步返回的 state 交给 simpWith。

于是三种能力，三种待遇，泾渭分明：

  • 只读背景（Env）：进得来、改不了。想局部换，用专门的带作用域的操作。

  • 可变状态（State）：读写都行，一步步接力往下传。

  • 失败（Error）：随时能抛，抛了就短路冒泡。

这三种效果具有不同接口。将它们都塞进一个大 State 虽然可以运行，却会丢失“只读”“可写”和“失败短路”的类型区分。

2.5.5. 还有第四种：会漏出去的效果🔗

再加一个例子，专门用来说明“回滚状态 ≠ 回滚世界”。假设我想让 tactic 一边跑一边打印调试信息（trace），或者跟外部工具通信。把这种“打印/对外交互”的能力也加进机器：

[伪代码]

带 IO 的机器 A  =  Env → State → IO ( 失败(Error) | 成功(A, State) )
                                    ^^ 这一步真的会向外部世界发生作用

IO 与状态的关键区别是：打印、文件写入和网络请求一旦执行，恢复 State 不会撤销这些外部效果。

加入 IO 后，pure 与 bind 也要提升到这一层。pure 产生不执行外部动作、直接返回成功值的 IO 动作；bind 先执行 m 的 IO，取得结果后再执行 k 的 IO。因此，两项操作都必须编排 IO 的顺序执行语义：

[伪代码]

pure(a) = fun env => fun state =>
  返回一个“不做对外动作，结果直接是 成功(a, state)”的 IO 动作

m >>= k   = fun env => fun state =>
  先真正执行 m(env)(state) 这一步 IO，得到结果 r     -- 这里会真的向外部世界发生作用
  match r with
  | 失败(e)         => 直接返回 失败(e)（IO 已发生，收不回）
  | 成功(a, state1) => 接着真正执行 k(a)(env)(state1) 那一步 IO

例如 trace("开始") >>= fun _ => simpWith(rules)：bind 先执行 trace，再运行 simpWith。即使后续 orElse 恢复 state，终端上的“开始”仍然存在。

因此，状态恢复只作用于 State 通道，不补偿已经执行的 IO。需要撤销外部效果时，必须另行设计事务或补偿机制。

2.6. 你刚发明的东西叫 monad🔗

到这里，Machine A 已具有参数化返回类型，并能承载状态、失败、只读背景与 IO。顺序组合需要两个操作：

  • pure(a)：把普通值 a 抬进机器，其余不动；

  • m >>= k（bind）：跑 m 拿到返回值，喂给 k 接着跑，自动传状态、自动短路失败。

一个类型构造器若配有满足特定规律的 pure 和 bind，就构成 monad。本章的 bind 来自顺序和值依赖组合中的公共样板。orElse 所需的选择与回滚不属于这两个基本操作。

因此，monad 不是本章额外塞进来的术语。then 暴露了状态接力与失败短路，findHyp 又要求把普通返回值交给下一步；pure 与 bind 正好概括这两类需求。这个来源比记住定义更重要，因为它同时说明了 monad 没有涵盖什么。

Lean 的 do 记法，就是 pure/bind 这条流水线的糖衣。以后你看到

[伪代码]

do
  let a ← m        -- 跑 m，把普通返回值绑给 a（这一行就是 m >>= fun a => ...）
  let b ← k a      -- 用 a 决定并跑下一台机器
  pure (a, b)      -- 把普通值抬回机器世界

就把它读成一串 >>=：每个 ← 底下都藏着一次 bind，替你传状态、传证明骨架、短路失败。这跟你手写的那串组合器一模一样，只是不用再自己接状态的链了。

2.6.1. monad 给你什么，不给你什么🔗

抽象有它的成本，也要标清楚它不管什么。把话说清楚，免得你把 monad 当万能钥匙。

monad 给你的：

  • 统一的顺序组合形状。不管返回值 A 是什么，所有机器长一个样、用一套 pure/bind 接力。then 和 allGoals 里反复出现的传值、传状态、失败短路因此能被抽掉。orElse 和依赖它的 repeat 还需要额外的“选择与回滚”接口；它们能和这套机器配合，却不能只凭 pure/bind 两个操作凭空造出来。

  • 自动的状态接力。bind 把上一步的新状态喂给下一步，你不再手写 state1 → state2 那条易错的链。

  • 在我们造出的这台 Machine 里自动短路失败。这里的失败层是我们自己放进 Machine 的，所以它的 bind 会让中途错误冒泡、跳过后续步骤；“任何 monad 都自带失败”则是错的，另一个没有失败层的 monad 完全可以没有这项行为。

  • 可预测的组合。这就是所谓 monad laws 的实际含义，别把它当三条天书。它们无非在保证：

[伪代码]

左单位：pure(a) >>= k        跟直接 k(a)          没区别
右单位：m >>= pure           跟直接 m             没区别
结合律：(m >>= f) >>= g       跟 m >>= (x => f(x) >>= g)  没区别

换成操作含义：pure 是组合中的单位元；一串 bind 重新加括号不会改变结果。因此，把中间步骤抽成辅助函数，或重组一个 do 块时，可以用这三条定律判断行为是否保持不变。

monad 不给你的（这几条踩坑率最高）：

  • 它不替你回滚。bind 只顺着走。要事务性回滚（orElse 那种“失败支的改动必须当没发生”），得靠你怎么组合状态与失败、以及显式的回溯组合器。把状态实现成可变引用后，回滚还得手动存档/回档。“包成 monad 了就自动能撤销”是错觉。

  • 它不把不同效果抹平成一种。只读背景、可变状态、失败、IO 是四种效果。“monad = 一个装状态的盒子”是把它看小了：状态只是它能承载的效果之一。

  • 它不让 IO 变得可回滚。状态能撤，打印出去的字撤不回来。

  • 它不替你分清“预期内的失败”和“真出错了”。tactic 说“这个目标我搞不定”（orElse 该据此换路）跟“证明系统本身崩了/接受了一个假证明”是完全不同的两回事。前者是正常搜索的一部分，后者是灾难。monad 的失败通道两种都能塞，但区分它们是你的责任，类型和 bind 不会替你分。这条到下一章会有真实后果。

2.7. 我们的机器 vs 现实：差距就是提升空间🔗

回到开篇那句话：我从头造出来这个东西，与现实那个东西的差距，就是我的提升空间。 现在盘点这个差距，它就是你读下一章的地图。

本章模型已经表达的内容：

  • 证明状态是一列目标，不是一个；空列表才算证完。

  • 每个目标 = 局部假设 + 待证命题，两者角色分明。

  • tactic 是状态转移：成功不承诺目标变少（intro 不变、constructor 变多、swap 只重排、skip 全不动）。

  • 关目标 = 往那张带洞的证明里合法地填结构，不是删列表项。

  • 顺序组合靠 pure/bind 抽掉状态接力和失败冒泡；orElse/repeat 另外要求选择与回滚语义，allGoals 另外要求遍历和聚焦目标。不同组合器各自需要什么，现在已经能分清。

  • 效果分为只读背景、可变状态、失败和 IO，接口与恢复语义各不相同。

本章模型没有表达的内容可分为两类：

一堆是纯工程加料，它们让机器更快更好用，但不改变上面这套心智模型：

  • 用可变引用存状态，以避免复制大状态；其代价是回滚需要显式存档；

  • 消息系统、trace、诊断输出；

  • 心跳/取消（跑太久就强行中断）；

  • 源码位置、报错定位、名字卫生；

  • 各种性能缓存。

另一堆会真正改写心智模型，它们不是“更快的同一台机器”，而是“更强、也更烧脑的另一台机器”，你现在的玩具直觉在这里会不够用：

  • 依赖类型：类型里可以出现值，“命题”和“证明”的界限比玩具里流动得多；

  • 元变量与赋值：现实中的洞由元变量承载。元变量身份各异，却跨目标共享约束；求解一个洞可能同时确定另一个。玩具模型省略的是这种依赖，而不是洞的身份；

  • 定义等价：assumption 需要专门的等价判定，该判定可能给元变量赋值并修改状态；

  • 精译：从有省略、有重载的表面语法，靠预期类型补全成完整核心项；

  • 语法与宏：tactic 得先被解析成语法树；

  • 实例综合：自动查找类型类实例；

  • 环境更新：往全局环境里加声明；

  • 内核检查：最终由独立内核检查证明对象是否合法。

看清这个分类，你就知道该把学习力气花在哪：第一堆照着查文档就能懂，第二堆才是真正拉开差距、值得反复琢磨的地方。

下一章要回答的问题，全是本章亲手挖的坑：

  1. 我那个 Env → State → 结果 的形状，在 Lean 里真的是这样叠出来的吗？叠了几层，为什么正好是那几层？

  2. 只读背景、可变状态和失败分别由什么结构承载？哪些数据只读，哪些数据可写？

  3. 那些“同一个构造子的洞”，元变量到底怎么跨目标把它们连起来、怎么赋值？

  4. assumption 里那句危险的“命题相同”，真实的“定义等价”判定危险在哪、副作用是什么？

  5. “成功的 tactic 不必减少目标”这条，Lean 的目标列表管理是不是真这么设计的？

  6. 状态换成可变引用后，Lean 如何实现事务性恢复？

下一章用 Lean 的实际类型和 API 回答这六个问题。阅读时不是重新背一套名词，而是逐项核对本章模型：哪些结构在现实中直接对应，哪些地方因依赖类型、元变量、可变引用和内核检查而必须修正。

2.8. 练习与设计题🔗

下面的题都不是背名词，是让你继续当那个“如果我来造会怎么造”的设计者。

  1. 造一个 exactMany。写出伪代码：它接收一列候选证明 [p1, ..., pn]，依次尝试用每个去关主目标，第一个成功就停。用 orElse 和 first 把它拼出来，别从头写循环。然后回答：它靠什么保证第三个候选失败时，不会污染第四个候选的现场？

  2. 给“成功不减少目标”再举个例。除了 constructor（变多）、swap（重排）、skip（不变），自己设计一个 tactic，它成功但目标数不变、却实实在在推进了证明骨架。提示：想想“把目标改写成一个等价但更好处理的形式”。

  3. 亲手触发回滚 bug。假设我们把 State 从“到处复制的值”改成“一个大家共享、原地修改的可变引用”。逐行推演：在这种实现下，t1 orElse t2 那个朴素版（“失败了就用原始 state 跑 t2”）为什么会出错？要修好它，orElse 在跑 t1 之前和 t1 失败之后，各需要多做一步什么？

  4. 把 repeat 用 orElse 和 pure 重写。给出伪代码，并说明为什么“做不动了”这一步必须返回失败之前的状态，而不是被半途改脏的状态。

  5. 区分两种失败。设计一段程序，它需要区别对待“assumption 没找到匹配假设（正常，应触发 orElse 换路）”和“我传给证明检查的对象根本不合法（异常，不该被 orElse 悄悄吞掉换路）”。你会怎么在失败通道里携带这个区别？为什么把两者混成一种 Error 会让 orElse 变得危险？

  6. 画出带洞证明的演化。取命题 P → (Q → (P ∧ Q))，用 intro、intro、constructor、assumption、assumption 一步步证它。每一步都把当时的“带洞证明骨架”完整写出来（洞用 <洞> 标记），并标注每个洞对应目标列表里的哪个目标。做完你会对“目标列表只是洞的索引”这句话有肌肉记忆。
